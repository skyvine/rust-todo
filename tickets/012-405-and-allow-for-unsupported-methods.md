# 012: Answer `405` with `Allow` for a known path and unsupported method

**Phase:** media types, headers, and status codes (after the redesign)
**Depends on:** 006, 007, 008, 009, 010
**Files:** `src/web_api.rs`, `src/lib.rs`

## Goal

A request for a method the server does not implement on an existing path is
told `405 Method Not Allowed` with an `Allow` header listing the methods that
do work — not `404 Not Found`, which claims the resource does not exist.

## Why this comes after the redesign

Whatever mechanism answers 405 needs to know which paths exist and which
methods each one supports. Written today, that knowledge is for paths the
redesign is about to replace. Land the URIs first and the mechanism is built
once.

## Background

Actix registers each attribute macro as its own resource with a method guard,
so a request for a registered path with any *other* method matches no resource
and falls through to the default 404 handler.

Verified against a running server, against a task that definitely exists:

```
$ curl -i -X DELETE "…/task_by_id?id=2424" -H "Authorization: Bearer $KEY"
HTTP/1.1 404 Not Found
```

RFC 9110 §15.5.6:

> The 405 (Method Not Allowed) status code is generated by the origin server
> when the method received by the server is known by the origin server but not
> supported by the target resource. […] The origin server MUST generate an
> Allow header field in a 405 response containing a list of the target
> resource's currently supported methods.

So this is a status-code bug, not only a style preference. A caller cannot
tell "I used the wrong verb" from "that task is gone", and gets no hint about
which verb to retry with.

This also applies to same-path method mismatches after the redesign — `PUT
/tasks/{id}`, `POST /tasks/{id}`, `PATCH /tasks`, and so on.

## In scope

- An unsupported method on a known path returns `405` plus a correct `Allow`,
  while genuinely unknown paths keep returning `404`.
- Actix does not group methods under one path across attribute macros, so one
  of these has to give:
  1. **Default service plus a path→methods table.** A `default_service` that,
     for a path matching a known resource whose method is not allowed, returns
     405 with `Allow` built from the table. Explicit and easy to test, but the
     table is a second place to update when routes change — so pair it with the
     test in the acceptance criteria.
  2. **Per-path stub handlers.** An explicit `#[delete("/tasks/{id}")]` whose
     handler returns 405 + `Allow`, for every method combination not
     implemented. Mechanical and local, but easy to forget one, and the
     combinatorics grow with each resource.
  3. **Scope with a nested router**, if the path groups can be restructured so
     methods are siblings of a single resource.
- `Allow` must list the methods actually registered for that path, not a
  hardcoded guess.
- `OPTIONS` and `HEAD` must keep working, or start working sensibly.

## Out of scope

- Adding `DELETE /tasks/{id}` so tasks can actually be deleted. That is a
  capability decision, made in ticket 005 and implemented in 006. This ticket
  makes the *absence* of the method honest; it does not change which methods
  exist.
- Content negotiation, where 405 also means "method supported, representation
  not". Not applicable — the API serves JSON only.

## Acceptance criteria

- [ ] `DELETE /tasks/{id}` returns `405` with `Allow` listing the methods
      `/tasks/{id}` actually supports (`GET`, `PATCH`, plus `DELETE` if 006
      adds it).
- [ ] `PUT /tasks` and `PATCH /tasks` return `405` with `Allow: GET, POST`.
- [ ] `POST /users/me` returns `405` with `Allow: GET`.
- [ ] `POST /health` returns `405` with `Allow: GET`.
- [ ] An unknown path such as `/nope` still returns `404`.
- [ ] A test asserts `Allow` matches the methods actually registered for every
      known path, so adding a route without updating the mechanism fails the
      suite instead of silently serving 404.
- [ ] `HEAD` and `OPTIONS` requests to known paths are unaffected.
- [ ] `cargo clippy` passes with no new warnings.
- [ ] `cargo test` passes.
- [ ] `cargo fmt --check` passes.

## Notes

`HEAD` deserves a decision before choosing a mechanism: actix answers `HEAD` for
any `GET` route by running the handler and dropping the body. A table-driven
default service that treats `HEAD` as unsupported would return 405 on a path
where `HEAD` works — which is the exact bug this ticket exists to fix, in a new
place.

Whether `GET /tasks/{id}` should also answer `HEAD` is worth deciding
explicitly rather than inheriting.
